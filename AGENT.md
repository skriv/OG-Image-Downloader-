# Agent instructions

All git commit messages must be in English only.

## Build

This extension is loaded from `dist/` in Chrome, not from source files.

After any change to popup, background, shared code, styles, or `popup.html`, **always rebuild yourself** before finishing:

```bash
npm run build
```

Do not ask the user to rebuild unless the build fails and you cannot fix it.

## Tests

Automated tests live in `test/*.test.mjs` and run with Node’s built-in test runner:

```bash
npm test
```

Rules for every code change:

1. **Run tests before finishing.** After fixing a bug or adding a feature, run `npm test`. Do not hand the work back while tests are failing.
2. **Add or extend tests with the change.** New behavior, bug fixes, and regressions need coverage in the matching suite (`extract`, `filename`, `download`, `zip`, `preview-i18n`, or a new focused file). Prefer one clear test per functional behavior.
3. **Keep pure logic in `src/shared/`** so it can be unit-tested without Chrome. Background/popup wiring may stay thin.
4. **Download/CDN bugs** must cover candidate URL building, image sniffing (reject HTML bodies), and filename extension correction — these are the failure modes behind Chrome’s “Site wasn’t available” / `.html` downloads.
5. Fixture HTML for DOM extraction is `test/fixture.html`. Playwright launches the system Chrome channel (`channel: "chrome"`) for extract tests so agents do not need `npx playwright install` unless that channel is unavailable.

If you touch download, extract, filename, zip, or i18n helpers and skip tests, the change is incomplete.

## Фронтенд UI: сначала skills, потом код

При любом построении, правке, ревью или полировке UI на фронте сначала прочитай и следуй skills из `.agents/skills/`. Не собирай интерфейс «из головы»: неверные easing, сплошные бордеры вместо полупрозрачных теней, слабая типографика и промахи по a11y — это то, от чего эти skills как раз защищают.

Стек проекта не меняй: React + Vite + Tailwind CSS v4 + HeroUI. Skills задают качество интерфейса, а не библиотеку компонентов.

Пропускай приветствия внутри skills (например «I'm ready to help…» в emil-design-eng). Нужны правила и реализация, не чат-интро.

### Обязательный набор при любой UI-работе

Перед тем как писать или менять UI, прочитай:

- `better-interface` — оркестрация: accessibility, layout, writing, typography, color, polish
- `better-ui`
- `better-layout`
- `better-typography`
- `better-colors`
- `better-accessibility`
- `better-writing`
- `heroui-react` — HeroUI v3 compound API, docs, theming (обязателен для UI на HeroUI)
- `emil-design-eng` — вкус, детали, motion
- `apple-design` — жесты, глубина, restraint, reduced-motion

Дальше дочитай узкий skill под задачу. Не заканчивай UI-задачу, пока не сверил результат с этими правилами.

### Когда какой skill

| Задача | Skills |
| --- | --- |
| Новый экран, компонент, страница | обязательный набор выше + `heroui-react` |
| Анимация, transition, «оживить» UI | `animate`, при необходимости `animation-vocabulary` |
| Проверить уже написанный motion | `review-animations` |
| Аудит motion по всему приложению | `improve-animations` (план, не патч) |
| Где анимация уместна, а где нет | `find-animation-opportunities` |
| Цвета, палитра, контраст | `better-colors` |
| Текст, подписи, ошибки, empty states | `better-writing` |
| Toasts | `ask-sonner` |
| Выбор библиотеки (не hand-roll) | `pick-ui-library` — но HeroUI уже выбран |
| Несколько вариантов UI | `variant` или `prototype` (только если пользователь явно просит) |
| Стресс-тест состояний компонента | `break` (только по явной просьбе) |
| Ревью diff / PR интерфейса | `interface-review` |
| Как собран чужой UI | `explain-interface` (только по явной просьбе) |

Не используй без запроса: `write-swift`, `animate-expo` (это не Swift и не React Native). `variant`, `break`, `prototype`, `explain-interface`, `interface-review` — только когда пользователь их просит или задача прямо про ревью/варианты.

### Порядок работы

1. Прочитай обязательные skills и узкий skill под задачу.
2. Реализуй в идиоме проекта (HeroUI compound API, Tailwind, существующие токены).
3. Проверь empty / loading / error / узкую ширину, hit areas, контраст, фокус, reduced-motion.
4. Если добавлял motion — проверь его правилами `review-animations` (ease-out на вход, не анимируй то, что не должно двигаться).
5. Перед сдачей сверьсь с `better-interface`: evidence, не вкус.
